# 音频链路审计与修复（2026-10-07）

本次验证的是 Aetheria 内部解码、处理、缓冲及提交给系统的 PCM 数据。
**不能据此认证“所有设备端到端无损”**：当前仍使用 CPAL 的系统输出，未实现
WASAPI 独占或 Android USB bit-perfect 输出，也没有测量各设备 DAC 的实际信号。

## 已修复的问题

| 环节 | 原问题 | 修改后的行为 |
| --- | --- | --- |
| 解码精度 | 32-bit PCM / F64 提前转换为 F32，低位丢失；部分 PCM 类型未实现而输出零 | 十种 Symphonia PCM 类型统一转换为 F64；未启用变调的链路保持 F64 至输出边界 |
| 整数输出 | 使用最大正整数缩放并截断，不能原样还原 PCM；无符号欠载静音为零 | 采用 2 的幂缩放、四舍五入及饱和；无符号静音为中点；整数码可精确表示时不加入抖动 |
| 输出协商 | 固定系统默认采样率且优先 F32 | 从后端声明的配置中优先选择立体声、足够精度及音源采样率；打开失败时继续尝试其他声明配置及系统默认配置；固定缓冲失败时尝试默认缓冲 |
| 降采样 | sinc 截止频率未随降采样比例降低，超出目标奈奎斯特频率的能量会混叠 | 增加与转换比例匹配的低通滤波、Blackman–Harris 窗及更长滤波器；新设置默认高质量，保留已存的用户选择 |
| 重采样连续性 | 每帧搬移缓冲、反复计算滤波系数，EOF 历史处理不完整 | 预计算多相系数，每块只整理一次缓冲；整数帧计数推导相位，块大小及空读取不改变输出 |
| 多声道适配 | 只取前两个声道，中心、人声及环绕声可能直接丢失 | 按声明的声道布局混合至立体声，包含中心、环绕、LFE，并按矩阵行和保留电平余量 |
| 队列 | 预填充放不下的已解码块被丢弃；超出容量的块无法入队；清空计数存在竞态 | 暂存未入队块；大块分段入队；清空数据与计数持有同一把锁；输出只消费完整声道帧 |
| 跳转 | 未重置解码器；定位到压缩包开头后未剔除目标位置之前的样本 | 成功 seek 后重置解码器与 SRC；按时间戳剔除包内前置帧 |
| 变调 | LiveShifter 固有延迟未补偿，末尾未完整冲刷；预填充与播放状态不连续 | 按原生 `getStartDelay` 剔除延迟，以零填充冲刷尾部，仅输出真实输入对应的帧数；预填充后将处理器独占所有权转交解码线程 |
| 保护 | 变调尾部绕过峰值保护；非有限值可能传到设备 | 尾部执行同样保护；NaN/Inf 输出为静音；正常范围且无需处理的样本不改变 |
| 设置说明 | 将应用流格式当作“设备格式”；抖动说明误将 F64 归入整数输出 | 标为“应用输出”，说明系统后续处理边界，以及音量、均衡和变调对波形的影响 |

没有增加新的运行时依赖，也没有改变 Flutter/Rust 公共接口。
Rubber Band 的转移仅实现 `Send`，不实现 `Sync`：原生实例不暴露别名，所有处理方法
要求独占可变引用，符合随项目提供的 `RubberBandLiveShifter.h` 的线程安全约定。

核心信号测试：

- 全部 65,536 个 I16 码值逐一往返一致；全部 U16 码值逐一往返一致。
- PCM16/24/32 WAV 在不同读取块大小下逐样本比较，包含极值和最低有效位。
- 独立 FFmpeg 生成的 24-bit 双声道 FLAC：20,000 个样本与生成公式完全相等；
  压缩包内 0.137 秒定位和返回起点均逐样本验证。素材与再生成方法在
  `rust/tests/fixtures/`，测试运行时不依赖 FFmpeg。
- 32-bit PCM 完整经过普通播放处理、预填充、队列及整数输出，样本数、顺序和码值一致。
- F64 WAV 不经过提前降精度；十种 Symphonia PCM 格式均单独覆盖。
- 5.1 每个输入声道的脉冲均能到达立体声输出，全声道满刻度合成不会超过满刻度。
- 欠载填入正确静音，部分声道帧不被消费，大于队列容量的块不丢样、不乱序。
- SRC 使用 17 帧与 2048 帧块的输出差异小于 1e-9，时长偏差不超过 1 个输出帧；
  期间插入空读取也不会破坏状态。
- LiveShifter 的两种窗口、1/129/2048/12001 帧输入输出时长一致；反复 finish 不重复尾部，
  reset 清除旧数据；跨线程转移保留状态；仅人声模式的左右差分信号在首尾仍精确对齐。

### SRC 信号测量

输入为 0.25 秒、峰值 0.5 的 F64 正弦；测量去除输出两端各 512 帧后的 RMS，
相对输入正弦 RMS 计算。下表是这些测试频点的混叠残余，**不是所有频率的统一指标**。

| 源采样率 → 输出采样率 | 输入频率 | 标准模式 | 高质量模式 |
| --- | ---: | ---: | ---: |
| 96 kHz → 48 kHz | 30 kHz | -139.96 dB | -142.58 dB |
| 192 kHz → 48 kHz | 30 kHz | -151.36 dB | -146.67 dB |
| 96 kHz → 44.1 kHz | 26 kHz | -116.96 dB | -155.33 dB |

高质量模式在 44.1→48、48→44.1、96→48、192→48 kHz 转换中，分别测试
1、10、20 kHz，幅度偏差均小于 0.1 dB。重采样本身必然改变样本，不能称为 bit-perfect。
预计算避免了原先每个输出帧反复计算三角函数和搬移缓冲，但本次没有对所有设备进行 CPU
占用或实时欠载压力测量；F64 中间缓冲内存约为旧 F32 的两倍。

## 仍需区分的边界

- 应用内逐样本无损成立的条件：无损输入、匹配采样率、保持原声道、不启用改变波形的 DSP、
  音量为 1、目标格式有足够有效精度、没有欠载或削波。
- 多声道目前明确折叠为立体声；CPAL 只有声道数而无完整扬声器映射。本次修复避免直接丢声道，
  没有实现多声道直通。折叠结果不能称为原多声道 bit-perfect。
- F32 能精确承载归一化 PCM24，不能精确承载所有 PCM32 码值；声明的 I32 容器也不能证明
  DAC 具有 32 个有效位。不得仅用“32-bit”或高采样率标签认证 Hi-Fi。
- 音量调整、响度均衡、变调、重采样和触发峰值保护均会改变波形。变调仍使用原生 F32 算法；
  输入有损压缩也不会因 F64 或更高输出采样率恢复原始信息。
- Windows 当前 CPAL 0.15.3 后端使用 WASAPI 共享模式，未实现独占；共享流进入系统音频引擎。
  参见 [Microsoft WASAPI 文档](https://learn.microsoft.com/windows/win32/coreaudio/wasapi)。
- Android 当前 CPAL/Oboe 路径只实现 I16/F32 输出，没有接入 Android 14 的 USB preferred
  mixer attributes / `MIXER_BEHAVIOR_BIT_PERFECT`；该能力也不是每条输出路由都支持。
  参见 [Android 高质量播放](https://developer.android.com/media/platform/improve-audio-playback)
  和 [AOSP USB mixer attributes](https://source.android.com/docs/core/audio/preferred-mixer-attr)。
- Linux 系统默认设备后面的混音、转换与音效，以及各平台蓝牙链路的实际编码，未由应用控制。
  本次未验证 Windows、Apple 平台、Android 实机、USB DAC 或蓝牙接收端的物理输出。

要认证某一设备端到端逐位无损，还需要实现/选择其直接输出通路，读取实际路由配置，并以数字回环
或接收端采样进行比对；模拟输出则需要独立测量频响、噪声和失真。当前测试结论不覆盖这些硬件认证。
